When a customer asks for an invoice for a sale already on a fiscal
receipt, the sale and its VAT were declared with the receipt; the
invoice is issued for accounting purposes only and goes to RO e-Factura
with type code **751** ("Factură — informații în scopuri contabile")
instead of 380.

The module adds the **Fiscal Receipt Number** to the point of sale
order, written by the register's driver once the receipt is printed, and
to the invoice, filled from the orders behind it. An invoice with a
receipt number is exported as 751; any other invoice, and every credit
note, keeps its usual type code. A point of sale without a register, or
one that sells on invoice only, prints no receipt: its invoices stay
380.

Use Cases / Context
===================

Key features
============

-  **Automatic type-code 751** — invoices that carry a
   ``l10n_ro_fiscal_receipt_number`` are exported to RO e-Factura as
   *Factură — informații în scopuri contabile*, as required by ANAF.
-  **Fiscal Receipt Number on POS orders** — the register's driver fills
   ``l10n_ro_fiscal_receipt_number`` on ``pos.order``; the value
   propagates automatically to the customer invoice.
-  **Manual override for back-office invoices** — accountants can type
   the receipt number directly in the invoice's *Other Info* tab before
   sending to the SPV.
-  **Field locked after SPV submission** — the receipt number (and
   therefore the e-Factura type code) cannot be changed once the invoice
   has been sent to ANAF, preventing inconsistencies.
-  **Non-intrusive** — invoices without a receipt number and all credit
   notes keep their standard type codes; no configuration is required
   after installation.

Configuration
=============

Nothing to set. The number is written on the order by the integration of
the fiscal register, once the receipt is printed, and reaches the
invoice generated from the order.

For an invoice issued later in the back office for a sale already on a
receipt, fill **Fiscal Receipt Number** in the invoice's *Other Info*
tab before sending it to ANAF.

Usage
=====

Flow 1 — Invoice generated automatically from a POS order
---------------------------------------------------------

1. The cashier completes the sale in Point of Sale. The fiscal register
   prints the receipt and its driver writes the receipt number into the
   **Fiscal Receipt Number** field on the ``pos.order``.
2. When the customer requests an invoice, generate it from the POS order
   in the usual way (*Point of Sale → Orders → Orders* → open the order
   → **Create Invoice**).
3. Odoo copies the receipt number into the invoice's
   ``l10n_ro_fiscal_receipt_number`` field automatically (computed from
   the linked POS orders).
4. Send the invoice to ANAF via *Accounting → Customers → Invoices* →
   open the invoice → **Send & Print** (or the e-Factura action). The
   UBL-RO XML is exported with type code **751** instead of the usual
   380.

Flow 2 — Back-office invoice for a receipt issued outside Odoo
--------------------------------------------------------------

1. Go to *Accounting → Customers → Invoices* and create or open a draft
   invoice.
2. Open the **Other Info** tab and fill in **Fiscal Receipt Number**
   (``l10n_ro_fiscal_receipt_number``) with the number printed on the
   fiscal receipt.
3. Confirm the invoice while it is still a draft (the field becomes
   read-only once the invoice has been sent to the SPV).
4. Send to ANAF. The XML is exported with type code **751**.

..

   **Note:** Invoices without a fiscal receipt number, and all credit
   notes, are exported with their standard type code (380 / 381). A POS
   terminal configured to sell on invoice only (no fiscal register)
   produces no receipt number; its invoices remain 380.
